### 傾向

#### Oracleが高速

- 複雑なJOIN かつ 集約するクエリ
- 事前集約済みデータの集約処理

#### PostgreSQLが高速

- 大量データのインデックス走査
- Bitmap Scan利用時
- 大量データ取得

---

### PostgreSQLで遅かったケース

- 複雑なJOIN かつ 集約するクエリ

---

### チューニング(次回以降の課題)

- Index追加
- SQL修正
  - 一部クエリの WHERE / BETWEEN を使用していたが、>, <= に変更する
  - to_char で変換している箇所を取得前後で対応する形に修正

---

### 結果

#### Oracle vs PostgreSQL

- 仕訳明細データ取得では 60% 以上、実行速度が改善した
- 精算表取得 / 結合クエリ側では、Oracle 側がやや速度が速い。
- 精算表取得 / 集約済みデータ側では、数ms レベルの誤差。

#### Oracle 結合クエリ vs 集約済みデータ

- 仕訳明細データ取得では、集約することによる改善が見られなかった。
- 精算表取得では、集約することによって、大幅に改善が見られた（85~98% 改善）

#### PostgreSQL 結合クエリ vs 集約済みデータ

- 仕訳明細データ取得で、事前集約することによって 20~50% ほど改善された。
- 精算表取得では、集約することによって、大幅に改善が見られた（85~98% 改善）

## 2. プロシージャ

### 比較結果

| proc_set_settl_m    | 1,000 |  4,000 |
| proc_set_settl_y    |     0 |     0 |

### 傾向

#### Oracleが高速

- 仕訳明細データから月別精算表を作成する proc_set_settl_m 内の処理

#### PostgreSQLが高速

- 仕訳明細データを作成する proc_set_journal の処理

---

### チューニング(次回以降の課題)

#### Oracle 側

- proc_set_journal の処理について、実行計画調査のうえ判断

#### PostgreSQL 側

- proc_set_settl_m の処理について、実行計画調査のうえ判断

---

### 結果

#### Oracle vs PostgreSQL

- proc_set_journal の処理で PostgreSQL 側では 10 秒以内で完了していたのに対し、
  Oracle 側で 4分強 掛かっていた。
  Oracle 側の実行計画に改善余地がある可能性がある。
  上述の通り、次回以降、Oracle 側の実行計画を調査のうえ、対応する。

- proc_set_settl_m の処理で Oracle 側では 1 秒以内で完了していたのに対し、
  PostgreSQL 側で 4秒ほど掛かっていた。
  今回のPoCではOracle側が高速だった。実行計画の違いが影響した可能性がある。
  次回以降、PostgreSQL 側の実行計画を調査したうえでの対応を予定。
